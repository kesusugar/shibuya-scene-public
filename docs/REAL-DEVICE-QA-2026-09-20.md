# 実機QA手順 — `codex/prebaked-motion` 第7段階の検証

この環境には音声デバイスがなく、WebGL は SwiftShader（約0.2fps）で動くため、**FPS・起動時間・見た目はここでは測れない**。
以下は オーナーの PC で実行してもらう手順。**壊れている可能性が高い順**に並べてある。

各項目に「見るもの」と「壊れていたときの症状」を書いた。症状が出たらその項目番号とスクショを返してもらえれば、原因の当たりを付けられる。

---

## 0. 準備

```powershell
git fetch origin
git switch codex/prebaked-motion
git pull --ff-only origin codex/prebaked-motion
npm ci
npm run dev:local
```

ポートは端末に出るものを使う（通常 5174）。以後 `http://127.0.0.1:5174/` と書く。

**開発サーバの数値と本番ビルドの数値を混ぜないこと。** 起動時間とFPSの合否は §6 の本番ビルドで取り直す。

---

## 1. 最優先：初回乗車で車が消えないか（第6段階）

**ここが今いちばん壊れやすい。** 詳細な車両モデル（raw 1.69MB / gzip 150KB）は、初めて車に乗るまで読み込まれない設計になっている。読み込み中は従来の簡易車両が表示され続けるはず。

```
http://127.0.0.1:5174/?tier=high&time=day&camera=scramble
```

1. 「プレイヤー」ボタンで入る
2. 車まで歩いて `F` で乗る
3. **乗った瞬間から数秒、車が消えないか**を見る

F12 のコンソールで状態を直接確認できる:

```js
__SHIBUYA_CAR__            // 車の state
```

**壊れていたときの症状**

| 症状 | 意味 |
|---|---|
| 乗った瞬間に車が消えて、数秒後に出てくる | 簡易車両の引き継ぎが効いていない |
| 車が**ずっと簡易表示のまま**（詳細にならない） | 動的 import が失敗している。コンソールに赤いエラーが出ているはず。**5秒のバックオフがあるので、失敗しても静かに再試行して、また失敗する** |
| 乗る→すぐ降りる→また乗る、で車が出てこない | 読み込み完了時の `active` ガードの取りこぼし |
| スクーターに乗ると詳細モデルにならない | これは**仕様**（コード上スクーターは詳細モデルを割り当てない）。異常ではない |

**必ず F12 のコンソールを開いたまま試すこと。** 動的 import の失敗は画面上は「何も起きない」ので、コンソールを見ないと分からない。

## 2. 近距離NPCの湧き方（第3段階）

近くの歩行者だけ、HIGH で最大32体がボーン付きのモデルになる。**1フレームにつき1体ずつしか増えない**設計なので、人混みに歩いて入ると約32フレームかけて順番に切り替わる。

1. プレイヤーモードで人が多いところ（スクランブル中央）へ歩く
2. 切り替わりが**目に見えてポップするか**を見る

**壊れていたときの症状**

| 症状 | 意味 |
|---|---|
| 近くの人が目の前でカクッと入れ替わる | 1フレーム1体の追加が目立っている。距離のしきい値（25m/30m）の調整が要る |
| 近くの人が**同じ服の色ばかり**になる | **これは現状の実装上そうなる。** 色は4種類しか用意されていないので、32体が4色に割り振られる。バグではないが品質上の課題（§実装案 A-1） |
| 品質を HIGH→LOW→HIGH と切り替えると人が消えたまま | `setTier` のプール破棄と再構築の取りこぼし |
| 遠くの人まで急に滑らかになる／重くなる | プール上限が効いていない |

## 3. 歩行者の危険予測（第4段階）

車の1.6秒先を予測して、退避方向が歩ける場所かを確認してから避ける。10Hz・最大64人。

1. 車でゆっくり人に近づく → 避けるか
2. **バックで**近づく → 避けるか（後退も予測対象のはず）
3. 曲がりながら近づく → 曲がった先の人が避けるか

**併せて音も確認してほしい。** 人が「あぶな！」「きゃーー！」と声を上げるはず（master にマージ済みの機能）。**この環境では誰も音を聴いていないので、実機での初聴になる。** 音量・声の高さ・不自然さの感想がほしい。

**壊れていたときの症状**

| 症状 | 意味 |
|---|---|
| 壁や車道側へ避けて詰まる | 退避先の歩行可否チェックが効いていない |
| 避ける動きがガクガクする | 10Hz の更新がそのまま見えている。補間が要る |
| バックでは避けない | 後退時の予測が効いていない |
| 声が鳴らない | プレイヤーモードに**クリックで**入っていない可能性（AudioContext はクリックでしか解錠できない） |

## 4. 車の接触応答（第5段階）

1. 壁に**斜めから**当たる → 法線方向に減速して接線方向へ滑るか
2. 正面から当たる → 止まるか。跳ね飛ばされないか
3. 信号待ちの車に当てる → めり込まないか
4. ハンドブレーキ、逆走、坂

**壊れていたときの症状**

| 症状 | 意味 |
|---|---|
| 壁に当たると飛ぶ／ワープする | エネルギー上限が効いていない |
| 壁沿いで損傷が一気に増える | 連打抑制が効いていない |
| 停車中に車が小刻みに震える | 四輪サスペンションの数値が発散している |
| 他の車を押せない | **これは仕様。** 他車は kinematic で、押し飛ばしは未実装（§実装案 B） |

## 5. 昼夜の見た目

`?time=day` と `?time=night` の両方で、固定カメラを一通り。

- 夜の看板が白飛びしていないか
- **人物が暗すぎないか**（引き継ぎ文書が懸念として挙げている）
- 車の足元が地面に沈んでいないか
- 影・カメラ遮蔽

昼夜それぞれでスクショをもらえると比較できる。

## 6. 起動時間とFPS（本番ビルドで）

**dev サーバの数値は使わない。** HMR が乗っているので本番と別物。

```powershell
npm run build
# 本番サーバを起動してから、そのURLで以下を実行
```

別の PowerShell で Chrome を CDP 付きで起動:

```powershell
& "C:\Program Files\Google\Chrome\Application\chrome.exe" `
  --remote-debugging-port=9222 `
  --user-data-dir="$env:TEMP\shibuya-qa-profile" `
  "http://127.0.0.1:5174/?qa=1&startupTiming=1&tier=high&time=day"
```

```powershell
npm run qa:capture -- --url http://127.0.0.1:5174/ --cdp-port 9222 --timeout-ms 300000
```

- **Chrome を前面に保つ**（hidden タブは除外される）
- `?startupTiming=1` がないと startup が null になる
- `?qa=1` は HIGH 固定。MEDIUM/LOW は通常 URL で別途

**コールド/ウォーム起動を各3回**、同じウィンドウサイズ・DPR・画角で。GPU 名と Chrome バージョンも記録してほしい（`chrome://gpu`）。

出力される `metrics.json` / `startup.json` / `console.json` を送ってもらえれば、どこが律速か判定できる。

## 返してもらえると助かるもの

優先度順:

1. **§1 の結果とコンソールのエラー** — ここが通らないと他が意味を持たない
2. 昼と夜のスクショ（プレイヤー視点、車に乗った状態、人混みの中）

4. `qa:capture` の `metrics.json` / `startup.json` / `console.json`
5. 「見ていて気持ち悪い」と感じた点。数値に出なくても、それがいちばん重要
