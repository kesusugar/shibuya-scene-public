# 参照画像から読み取れること、そして足りないもの

参照: Cabsolutely のプレイ画面1枚（`https://github.com/ilkerzg/cabsolutely`、MIT、`LICENSES/cabsolutely.txt` に記載済み）

---

## 0. 最も重要な観察

**この画像にはHUDが1つも写っていない。**

ミニマップも、速度計も、ミッションパネルも、ボタンも、体力表示もない。上下に黒帯（レターボックス）が
入っているだけ。

それでも「UI/UXのレベルが高い」と感じられる。つまり、ここで体験を作っているのは
**HUDではなく、世界そのものが情報を伝える設計（diegetic UI）** である。

> 注意: これは1フレームからの読み取りであって、「Cabsolutely にHUDが存在しない」と断定するものではない。
> 撮影時に隠していた可能性も、演出上の一場面である可能性もある。
> ただし**この画像を「目指すもの」として提示された以上、この画像が実際に持っている性質**を分析する価値はある。

画面内で実際に仕事をしている要素:

| # | 要素 | 役割 |
|---|---|---|
| 1 | **路面標示** — 黄色センターライン、白破線、路肩の白実線、路面に描かれた大きな文字（TAXI / BUS） | **これが経路案内そのもの。** ミニマップを見なくても、どこを走るべきかが路面から読める |
| 2 | **カメラの画角** | 車の前方の路面が広く見える。次の判断に必要な情報が画面内にある |
| 3 | **運転席に人が座っている** | 車が「操作されている物体」に見える。空の箱ではない |
| 4 | **マテリアルの明確な分離** | 歩道タイル / アスファルト / ガラス / 樹木が、色でなく質感で区別できる |
| 5 | **街路設備の密度** | ゴミ箱・ベンチ・車止め・街路樹が連続して並び、スケール感を与えている |

**HUDを足すより、この5つを埋める方が体験は上がる。**

## 2. 重要な注意 — 参照画像をそのまま真似してはいけない

参照画像は**英語圏の街**で、路面に `TAXI` `BUS` とローマ字で書かれている。

**渋谷でこれをやると嘘になる。** 日本の路面標示は:

- 「止まれ」（停止線の手前）
- 「バス」（バス専用レーン）
- 数字の速度表示（「40」など）
- ひし形（横断歩道あり予告）
- 白の破線・実線、**中央線は黄色（追越し禁止）または白**
- 導流帯のゼブラ

このプロジェクトは「実在の渋谷の再現」を掲げていて、看板の文字も実物に忠実にする方針を取っている。
**路面だけローマ字にするのは方針と矛盾する。**

参照から取るべきなのは**「路面が経路を語る」という考え方**であって、書かれている文字ではない。

## 3. プラン

### P0 — 路面標示を道路の全長に伸ばす ★最大の効果

**これが1番効く。** 走っている間ずっと目に入り、ミニマップを見る回数を減らし、街を「道路」に見せる。

実装の見通しは良い。**既存の仕組みがそのまま使える**:

- `zebra(points, width, road)` が既に「ポリラインに沿って一定ピッチで短冊を置く」処理をしている。
  破線はこれと同じ形。`pitch` と `stripe` を変えるだけ
- 道路の中心線 `points` は `ground/model.mjs` が既に持っている
- 塗装は `intersection(rect(...), roads)` で道路面にクリップする方式が確立している

作るもの:

1. **中央線** — 道路の中心線に沿った連続帯。幅 0.15m 程度
2. **車線区分の白破線** — 幅の広い道路（`mainWidth` 以上）で、中心から車線幅ごとに
3. **路肩の白実線** — 道路ポリゴンの境界から内側に一定距離
4. **路面の文字**（第2段階）— 「止まれ」「バス」。ポリゴンで作るなら `arrows` と同じ手法が使える

> ⚠️ **`src/ground/model.mjs` は `STATIC_ROOTS` に入っている。**
> 触ったら `npm run bake:static` が必須で、事前生成キー `25ea9435...` が動く。
> これは**正当な変更**なので焼き直してよいが、焼き忘れると全ユーザーが起動時に幾何を再生成する。
> 変更後に必ずキーを確認し、コミットメッセージに「キーが動いた理由」を書くこと。

**黄色が必要になる。** 現在 `paint` マテリアルは白1つだけ。選択肢:

- (a) 黄色のマテリアルを1つ足す → バッチが5→6に増える。最も単純
- (b) `paint` を vertex color 対応にして1バッチのまま2色 → バッチは増えないが実装が複雑

群衆と違って ground には 13/3 のような契約テストはないので、**(a) で十分**。

### P1 — 運転席に人を乗せる ★費用対効果が非常に高い

参照画像で「生きている」と感じる大きな要因。そして**実装は驚くほど安い**。

- AI車: `traffic/render.mjs` は車種ごとにインスタンシングしている。
  **全車種共通の「座った人」メッシュを1つ** `InstancedMesh` で足し、
  走行中の車の座席位置に置くだけ。**追加バッチは1、追加マテリアルは0〜1**
- 自車: 運転中はプレイヤーの figure が隠れるので、**外から見ると自分の車も空**。
  同じインスタンスを自車にも1体置けば解決する

頭と肩だけの簡略形状で十分。窓越しにシルエットが見えることが重要で、顔は見えない。

### P2 — カメラを詰める

現状（`codex/prebaked-motion`）:

```js
followBack: 9.8   // 車の後方9.8m
followUp:  3.6    // eye(1.4) と合わせて約5.0m上
ahead = 2.8 + min(2, speed*0.12)   // 注視点は車の2.8〜4.8m前
FOV = 50°
```

俯角は約16°。**参照画像はこれより近く、角度が深い**（車が画面に占める割合が大きく、前方の路面がより広く見える）。

> **断定はできない。** 1枚の画像からFOVと距離を分離して測ることはできない。
> **数値を実機で調整できる形にして、オーナーに決めてもらうのが正しい。**

提案: `?cam=back:7,up:3,ahead:6` のようなURLパラメータで、走りながら比較できるようにする。
**見ないと決められないものは、見ながら決められる形にする。**

### P3 — HUDは「足す」のではなく「引く」

参照画像にHUDがないことの含意は、**常時表示を減らすべき**ということ。

現在のHUD（`src/player/play-ui.mjs`）は、ミッション未開始でも
ミッションパネル・ミニマップ・ダッシュボードが**常に全部出ている**。

提案する表示規則:

| 要素 | 出す条件 |
|---|---|
| 速度計 | 運転中のみ |
| 損傷 | 損傷 > 0 のときのみ |
| ミニマップ | ミッション中のみ（または `M` でトグル） |
| ミッションパネル | ミッション中、または開始可能な場所にいるとき |
| 体力 | 減っているときのみ |
| 操作説明 | 初回のみ自動 → `Tab` で再表示（既存のUIプランの §1-2 と統合） |

**何も起きていないときは、画面に何も出ない。** それが参照画像の状態。

## 4. 優先順位のまとめ

| 順位 | 項目 | 効果 | 工数 | リスク |
|---|---|---|---|---|
| 1 | 路面標示（中央線・破線・路肩） | **大** | 中 | 事前生成キーが動く（正当） |
| 2 | 運転席の人 | **大** | 小 | 小 |
| 3 | HUDを条件表示に | 中 | 小 | 小 |
| 4 | カメラ調整パラメータ化 | 中 | 小 | なし |
| 5 | 路面の文字（日本語） | 中 | 大 | キーが動く |
| 6 | 街路樹の密度調整 | 小 | 小 | 実際の渋谷は樹が少ないので、忠実性と要相談 |

1 と 2 は**実機を見なくても正しさが確認できる**（標示が道路面にクリップされているか、人が座席位置にいるかは
数値で検証できる）。3 と 4 は実機で判断が要る。
