# UI品質向上プラン

実機を見ずに、コードを読んで確認できた事実のみに基づく。**「見た目が悪い」という推測は含めない** —
レンダリング結果は誰も見ていないので、ここに書くのは「コード上そうなっていることが確実な欠陥」と、
その修正案だけ。

対象: `app/globals.css`（156行）、`app/ShibuyaScene.tsx`、`src/player/play-ui.mjs`、`src/player/touch-controls.mjs`、`src/player/diagnostics.mjs`

---

## 0. 現状のUIの実像

UIは**3層が別々の仕組みで同居**している。

| 層 | 実装 | 表示条件 |
|---|---|---|
| 検査UI（サイドバー、13個のJSONダンプ、固定カメラ一覧） | React / `ShibuyaScene.tsx` | `inspection` モード |
| 発表UI（ヘッダ、カメラ切替、時間帯、stats） | React + `.presentation` CSS | `presentation` モード |
| **ゲームHUD**（ミッション、ミニマップ、ダッシュボード） | **素のDOM** / `src/player/play-ui.mjs` | `mode==="player"` で `.playing` |

`.playing` は header / quick-views / solar-controls / stats / view-label / **player-hint** を
`display:none!important` で消す。つまり**プレイ中は React 側のUIが全部消え、素のDOMのHUDだけになる。**

これ自体は妥当な設計。問題は、2つの世界が**デザイン言語を共有していない**こと（§2-1, §2-2）。

## 1. 確定しているバグ

### 1-1. 存在しない機能を案内している ★最優先

`src/player/play-ui.mjs:8`

```js
<div class="play-brand">SHIBUYA <span>FREE ROAM · Tab メニュー</span></div>
```

**`Tab` のキーハンドラはリポジトリ内のどこにも存在しない。** 画面が案内している操作が何も起きない。

修正は2択:
- (a) 表記を消す — 5分
- (b) Tab メニューを実装する — §3-2 の操作説明パネルをここに割り当てるのが自然

### 1-2. プレイ中に操作説明が一切出ない ★最優先

`app/globals.css`

```css
.playing .player-hint{display:none!important}
```

`.player-hint` は「WASD で移動 ・ Shift で走る ・ E/クリックで攻撃 ・ F で乗る ・ Esc で観察に戻る」を出す
唯一の場所。それが**プレイに入った瞬間に消える。** HUD 側に代替はない。

初見の人は、**操作方法を知る手段がゼロ**。

### 1-3. 体力表示に操作説明が混入している

`src/player/play-ui.mjs`

```js
health.textContent=`体力 ${...} · E/クリック 攻撃`;
```

体力という**状態**と、攻撃キーという**操作説明**が1つの `<small>` に同居している。
1-2 の穴を塞ぐための応急処置に見えるが、体力が減っていくたびに操作説明も一緒に再描画される。

### 1-4. ミニマップの範囲外ターゲットが区別できない

`src/player/play-ui.mjs` の `dot()`

```js
const x=Math.max(8,Math.min(312,160+(p.x-position.x)*k)), y=...;
```

目的地が地図の範囲（半径90m）の外にあると、**縁にクランプされて止まる**。
これは「縁のすぐ内側にある目的地」と見分けがつかない。距離感が壊れる。

### 1-5. iPhone横持ちでノッチに被りうる

```css
.play-top{top:max(16px,env(safe-area-inset-top));left:20px;right:20px}
```

上方向だけセーフエリアを見ていて、**左右が20px固定**。iPhone を横に持つとノッチは左右に来るので、
「観察に戻る」ボタンかブランド表示がノッチの下に入る。横持ちでプレイする前提なら実害がある。

## 2. 一貫性の欠如（見た目の質に直結）

### 2-1. カラーシステムが2つある

`:root` にトークンが定義されている:

```css
--background:#10151d; --foreground:#e4edf3; --primary:#60cee2;
--primary-foreground:#06151c; --input:#435569; --ring:#60cee2
```

しかし**HUDはこれを1つも使っていない。** HUD内で直に書かれている色:

```
#eef5f6 #16372f #d9fff0 #8fddba55 #0b1724dd #ffffff22 #68e7b4
#c4d4dc #a8ffd5 #cadce044 #0c1821dc #bacbd1 #9ff0bd #cad8df #70d7ff #354d5b
```

**16色が個別に散っている。** 検査UI側は青系（`#60cee2`）、HUDは緑系（`#68e7b4`）で、
同じアプリの中で系統が違う。片方を変えても、もう片方は追従しない。

### 2-2. 日本語フォントが未指定

```css
body{font-family:Arial,"Noto Sans",sans-serif}
.play-hud{font-family:Arial,sans-serif}
```

**日本語フォントが1つも指定されていない。** 「渋谷デリバリー」「体力」「観察に戻る」は
全部ブラウザ任せのフォールバックで描かれる。Windows なら Yu Gothic UI、Mac なら Hiragino、
Android なら Noto Sans CJK と、**環境ごとに字面も字幅も変わる。**

さらに HUD だけ `"Noto Sans"` が抜けていて body と違う。

> Webフォントのダウンロードは避けること。起動時間を最優先とする方針と、
> 第三者アセットを無断で入れない方針の両方に抵触する。**システムフォントの指定だけで解決できる。**

### 2-3. 文字サイズが9段階ある

HUD 内だけで `9px / 10px / 11px / 12px / 14px / 16px / 22px` が使われている。
階層が設計されていないので、「どれが重要な情報か」が大きさから読み取れない。

### 2-4. `<progress>` のスタイルがブラウザ依存

```css
.play-progress{width:100%;height:5px;accent-color:#68e7b4}
```

`<progress>` の見た目は Chrome / Safari / Firefox で実装が違い、`accent-color` だけでは揃わない。
高さ5pxの指定が効かないブラウザもある。

### 2-5. `.player-down`（やり直す）がHUDの体系外

`.playing` で消されないので、プレイ中の被弾時にHUDと一緒に出る。
しかしスタイルは検査UI時代のもので、HUDのガラス質（`backdrop-filter:blur(8px)`、`#0b1724dd`）と揃っていない。
**ゲームで一番感情が動く瞬間に、一番浮いたUIが出る。**

## 3. 改善プラン（優先順）

### P0 — 嘘と欠落を消す（見積もり 半日）

1. **「Tab メニュー」を実装するか、表記を消す**（§1-1）
2. **操作説明をHUDの正式な要素にする**（§1-2）
   - 提案: プレイ開始時に数秒だけ自動表示 → フェードアウト。`?` キーと、HUDの小さなボタンで再表示
   - 徒歩時と運転時で内容を出し分ける（React 側の `.player-hint` が既にその分岐を持っているので、ロジックはそのまま移せる）
   - これを `Tab` に割り当てれば §1-1 も同時に解決する
3. **体力から操作説明を分離**（§1-3）
4. **ミニマップの範囲外ターゲットを矢印に**（§1-4）— 縁でクランプするときだけ、丸でなく外向き三角を描く
5. **左右のセーフエリア対応**（§1-5）— `left:max(20px,env(safe-area-inset-left))` と right 側も同様

### P1 — 一貫性を作る（見積もり 1日）

6. **HUDの色を `:root` のトークンに集約**（§2-1）
   - `--hud-surface` / `--hud-border` / `--hud-text` / `--hud-dim` / `--hud-accent` / `--hud-danger` / `--hud-car` 程度で足りる
   - 16個の直書きを7個のトークンに畳む。**以後、配色の調整が1箇所で済む**
   - 検査UIの青系とHUDの緑系のどちらに寄せるかは、実機を見てから決めてよい。トークン化しておけば切替は一瞬
7. **日本語フォントスタックを整備**（§2-2）

   ```css
   --font-ui: system-ui, -apple-system, "Segoe UI", "Hiragino Sans",
              "Yu Gothic UI", "Noto Sans JP", "Noto Sans", sans-serif;
   ```

   body と `.play-hud` と `.dg`（診断パネル）と `.tc`（タッチUI）に同じものを適用。**ダウンロードは発生しない**
8. **文字サイズを4段階に整理**（§2-3）— 例: `--text-xs:11px / --text-sm:12px / --text-md:14px / --text-lg:22px`
9. **`<progress>` を div 2枚のバーに置換**（§2-4）

### P2 — 情報設計（見積もり 1〜2日）

10. **HUDの更新レートを分離**

    現在は `clock<.2` で**全部まとめて5Hz**。つまり速度計も200msごとにしか動かない。

    ```js
    clock+=dt; if(clock<.2)return; clock=0; draw(...);   // ← 地図も数値も全部この後ろ
    ```

    - 速度・体力・損傷 = 毎フレーム（テキスト更新は安い）
    - ミニマップ = 5Hz のまま（ここが重い）
    - ミッション文言 = 変化したときだけ

    **速度計が滑らかに動くだけで「作り込まれている感」は大きく変わる。**

11. **`.player-down` をHUDの体系に統合**（§2-5）
12. **ミッションパネルの状態を視覚化** — idle / running / complete / failed で左ボーダーの色を変える
    （既に `border-left:3px solid #68e7b4` があるので、色を状態に連動させるだけ）

### P3 — 表現を足す（実機を見てから）

13. ダメージ・接触時の画面端フラッシュ
14. `prefers-reduced-motion` 対応（**現在リポジトリ全体で未対応**）
15. ミニマップの進行方向回転モード切替

## 4. 実機なしでどこまでやれるか

**目で見なくても正しさを確認できるもの**（＝今すぐ着手してよい）

- §1-1 存在しない案内の削除
- §1-5 セーフエリア

- §2-4 `<progress>` 置換

**目で見ないと判断できないもの**（＝実機確認まで待つべき）

- §2-3 文字サイズ階層（何を大きくすべきかは見ないと決まらない）
- §3-2 操作説明の出し方（邪魔になるかどうかは体感でしか分からない）
- §3-12〜15 表現全般
- 青系／緑系どちらに統一するか

## 5. 検証方法

UIには現在テストが1件もない。以下は**実機なしでテストできる**:

- `.play-hud` 内に直書きの16進カラーが残っていないこと（トークン化の退行防止）
- 全UIコンポーネントが同じ `--font-ui` を参照していること
- `play-ui.mjs` の `innerHTML` に「Tab」など未実装の操作名が含まれないこと
- HUDの数値更新が地図更新と別レートで走ること

文字列レベルの検査なので、`tests/` に既にある `core-readability.test.mjs` と同じやり方で書ける。
